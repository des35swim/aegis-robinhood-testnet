# ADR 0004: AgentCore service boundaries

- Status: Accepted for prototype; deployment validation deferred to Phase 1
- Date: 2026-09-15
- Accepted by project owner: 2026-09-20

## Context

AgentCore Gateway can authenticate JWT or IAM callers, front Runtime, invoke Lambda targets with a Gateway IAM role, apply default-deny Cedar/Dogwood policy, and propagate a caller/session Workload Access Token across same-account, same-Region Gateway/Runtime hops ([inbound authorization](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-inbound-auth.html), [outbound authorization](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html), [policy sessions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-session-based-temporal.html)). Runtime can be restricted against direct bypass ([Runtime security](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-security-best-practices.html)).

## Decision

Use two physical Gateways in one AWS account and Region (`ap-southeast-2`):

1. **Ingress Gateway** — Cognito/OIDC JWT inbound authorization, restrictive scopes, request/response controls, and an AgentCore Runtime HTTP target.
2. **Tool Gateway** — accepts only the propagated AgentCore workload identity from Runtime and exposes narrow read/proposal/execution-preparation Lambda targets. It has an attached default-deny Policy engine.

Human approval/rejection and wallet-submission reporting are separate authenticated API Gateway/Lambda endpoints. They are not AgentCore tools and are not callable by Runtime.

Runtime receives no DynamoDB table access for authoritative financial state, no signing permission, no Secrets Manager read for RPC/API credentials, and no direct blockchain egress. Tool Lambdas use distinct roles. Only the executor/preparation role can conditionally claim a stored proposal, and it cannot sign.

Use a per-conversation policy-session ID generated by the application. DynamoDB is authoritative for proposal state, approval, expiry, exposure reservations, and replay protection; temporal Dogwood rules provide defense-in-depth sequencing only.

## Bypass prevention

- Ingress Gateway uses JWT authorization; Runtime uses IAM for its Gateway target relationship.
- Runtime's resource policy permits invocation only from the Ingress Gateway role and explicitly omits public/client principals.
- Tool Gateway target Lambdas permit invocation only from its Gateway role.
- Executor preparation rejects calls without the propagated principal/session context and independently loads actor/wallet from trusted state.
- CI must prove direct Runtime, direct tool Lambda, cross-user proposal, missing-session, and unknown-tool denial.

## Network boundary

Place Runtime in VPC mode without general internet egress. Owned services are reached through private AWS paths/endpoints where supported. External Robinhood RPC/API access is confined to adapter Lambdas with destination-aware egress controls and credentials from Secrets Manager. AWS documents that VPC-mode Runtime has no internet access unless NAT/routing is added ([Runtime VPC connectivity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-vpc.html)).

## Consequences

- Two Gateways add deployment objects but create a clearer principal and policy boundary.
- All AgentCore components participating in temporal sessions must stay in the same account and Region.
- Phase 1 must test WAT propagation and the exact IAM/resource-policy condition keys rather than assume them from diagrams.
- If a service limitation blocks the second Gateway, one physical Gateway may be used only after this ADR is superseded with equivalent logical separation and bypass tests.
